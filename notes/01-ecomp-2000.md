# 01 — ECOMP, 2000

Source: `erlang.org/euc/00/processor.ppt`, Erlang User Conference 2000. Robert
Tjärnström (Ericsson Radio) and Peter Lundell (Ericsson Telecom). Fifteen
slides, 473 words, created 30 Aug 2000, last saved 2 Oct 2000, 75 revisions.

**This deck is the entire public record.** No paper, no patent, no thesis, no
retrospective. Absent from EUC'99 and EUC'02 proceedings. Zero hits for
"ECOMP" in Armstrong's HOPL III *A History of Erlang*.

## What the slides say

**Motivation.** Increasing use of Erlang; eliminating performance and power
concerns; low power matters in embedded control; simplify Erlang for embedded
control; **eliminate the cost of a real-time operating system**; provide
run-time functionality.

**ISA.** Optimised for function call, return, argument transfer, list
operations. *"Clean register file upon start of new function"* — no
read/write-back of variables needed, exploiting single assignment so nothing
needs saving or restoring across a call. Supports processes and local scope.
**Three sub-instructions in each machine instruction**, each a (Tag, Value)
pair. **Sub-instructions for garbage collection.**

**Microarchitecture.** RISC, LIW, Harvard, 3–5 pipeline stages. Explicitly not
superscalar; no out-of-order, no speculation, no branch prediction *("but will
be added")*.

**Concurrency and GC.** Real-time GC performed concurrently in hardware.
*"Currently supports one element size."* Hardware-supported process switching,
**~20 cycles**. One process queue (design allowed more). **A clock-cycle limit
for each process.** Basic type checking. "Prepared for multi-threading."

**Runtime.** Switch, spawn, send, message-queue handling, catch/throw, timeout,
external IO, atom handling, registered processes — **implemented in machine
code**. Plus BIFs (`element`) and standard libraries (`lists`, ETS).

**Prototype.** A hardware model of the processor *developed in Erlang*, then a
VHDL implementation and testbench, then an FPGA demonstrator. PCI board with a
Xilinx XC40150 and four banks of 2 MB SRAM. *(The embedded slide image is named
`rc_1000_pp.jpg`, which points at a Celoxica RC1000 — the standard
XC40150 + 4×2MB PCI card of that era. The slides never name the board. Inferred,
not stated.)* Hosted from Windows NT; host↔board messaging via a loadable DLL
at **~7 µs/message average**, using the external Erlang term format. IO
processes ran on both host and board.

**Results.** ~3–4 machine instructions per line of Erlang. *"An approximate
speed-up of a factor 30 can be seen — measured per use of clock cycles."* Note
the hedge; an FPGA at tens of MHz against a contemporary 500 MHz CPU lost badly
in wall-clock and they knew it. Larger benchmark: call control, 16 KLOC,
714 k dump. "Increasing performance while decreasing power with more than an
order of magnitude."

**Roadmap.** Compiler improvements, product integration, distributed control
node, full-scale version, multi-threaded processor, *"Prepare for Silicon
Implementation."* It never got there.

## Why it died

Thomas Lindgren, erlang-questions, July 2005
(`erlang.org/pipermail/erlang-questions/2005-July/016355.html`): the goal was
"a *core* so that you could easily drop an 'Erlang machine' into any ASIC,"
constrained on area, memory and power — and **"what was missing was a large
enough market for Erlang-controlled ASICs."**

Context: Erlang had been banned for new product development inside Ericsson in
February 1998. A bet on Erlang silicon was being made against the company's own
policy. Meanwhile HiPE was landing at the same conference and delivering much
of the speedup with zero silicon risk.

## Verdicts, applied line by line

| Verdict | Idea | Reasoning |
|---|---|---|
| **Keep** | Uniform heap cell ("one element size") | Bacon's stall-free FPGA collector independently landed on the same simplification in 2012 ("miniheaps"). It is what makes a hardware collector small: pointer arithmetic is a shift, the free pointer is one register. |
| **Keep** | Concurrent hardware GC | Best-evidenced idea in the space. Bacon: <0.7% of Virtex-5 slices, zero mutator stalls, 100% utilisation at 1.01–1.4× live data. Cloaca (2024): ~20-cycle pauses, 4.1% of GHC's GC wall-clock at 1/25th the clock. |
| **Keep** | Reduction budget in hardware | A per-process cycle counter is nearly free and it is the whole preemption story. In a barrel machine it becomes an *exact* guarantee rather than an approximate one. |
| **Beat** | ~20-cycle process switch | Barrel multithreading makes a switch between resident processes cost **zero** cycles. Good for 2000; today it is the number to embarrass. |
| **Repurpose** | Sub-instruction slots for GC | With a collector on the second BRAM port the mutator owes GC nothing. Spend the third slot on OTP housekeeping instead — one mailbox-enqueue step, one exit-signal hop, or one timer-wheel tick per bundle. Supervision becomes rate-guaranteed rather than best-effort. |
| **Drop** | One process queue, one node | A single shared queue is the wrong shape for fabric. Fabric is spatial; Erlang is spatial. Per-engine queues and per-engine heaps. |
| **Drop** | Runtime in machine code | Their spawn/send/mailbox were software on top of the ISA. That is exactly the layer to sink into gates, and the layer nobody has sunk. |
| **Drop** | The throughput argument | PLM-vs-SPUR: 2.31×. Azul abandoned Vega for software barriers. Argue on bounds. |
