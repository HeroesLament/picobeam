# 17 — M4: the mailbox

The plan, written before the RTL, as 16 was. M4 per `07-roadmap.md`:
**serialiser, mailbox BRAM, shape hash, match unit on port B; still
single-engine, so `send` is a local loopback — which is the right way
to debug it.** Exit demo: ping-pong between two processes, with a
measured receive-latency distribution.

This is the milestone where picoBEAM's processes stop being merely
concurrent and start being *Erlang* processes: isolated things that
communicate only by copied messages.

## What the model already fixes

`machine.ex` implements the whole receive protocol, and the RTL's job
is to earn it:

    recv_start          cursor = 0, filter = none
    recv_hash H         filter = H (the assembler computes H)
    recv_peek rd, none  scan from cursor for the first message whose
                        shape hash passes the filter; found → rd = word,
                        cursor = that index; none → cursor = end, jump
    recv_skip           cursor = cursor + 1
    recv_take rd        remove the message at cursor, cursor = 0,
                        filter = none
    recv_wait[t]        block until a message arrives past cursor
                        (or the timeout fires)

That is BEAM's receive loop with the scan lifted into hardware. The
`recv_hash` filter is an OPTIMISATION, never a decision: the real
pattern match is ordinary code the compiler emits after `peek`. A hash
collision therefore costs a wasted peek, never a wrong match — which is
what lets the hash be cheap.

## Decision 1 — the shape hash is a hardware contract, not phash2

The model uses `:erlang.phash2/2`. That is not synthesisable, and both
ends must agree exactly: the ASSEMBLER computes the filter for
`recv_hash` at compile time, and the MAILBOX WRITER computes the
arriving message's hash in gates. So the hash joins the opcode table as
a thing with one definition and two consumers, and the model moves —
the same trade the heap's cell addressing took at M2.

The shape of a term, for matching purposes, is what BEAM's receive
actually discriminates on:

    {kind, arity, first_atom}

`kind` ∈ {immediate-atom, tuple, cons, other}; `arity` and the leading
atom index only exist for tuples. A deterministic 8-bit packing —
kind in the top bits, arity and the leading atom's low bits below — is
enough, because collisions are free and the field is only 8 bits wide
in the instruction anyway. `Encoding` gains `shape_hash/1`, the RTL
gains a tiny combinational block, and a tripwire script proves they
agree on every shape the assembler can express.

## Decision 2 — take is a tombstone, not a shift

`recv_take` removes from the MIDDLE of the mailbox (at the cursor, not
the head), which a ring buffer cannot do cheaply and a linked list does
at the cost of pointer chasing. Hardware takes the third option: every
entry carries a valid bit, `take` clears it in place, and the head
advances past invalid entries lazily. Take is O(1), the scan skips
tombstones, and the ring survives — no allocator, no pointers, no
compaction pass.

Storage: `{slot:5, idx:6}` → 2048 entries of 36-bit word + 8-bit hash +
valid, mailbox depth 64 per process, matching the model's default.
About 5 EBRs on top of M3's 41.

## Decision 3 — the scan parks its context, and that IS "free"

`05-determinism.md` claims the matcher costs the mutator nothing
because it runs on the mailbox's second port. In a barrel that claim
takes its most literal form: `recv_peek` PARKS the scanning context and
runs the scan FSM while **the other three seats keep executing**. The
scanning process pays scan-distance turns; every other process pays
nothing. The claim is structural again, not empirical — and the park is
the same F-slot claim pattern that call, ret, spawn and swap already
use, so it needs no arbiter for the sixth time.

`stats.scans` in the model becomes a real histogram: the demo measures
scan distance on hardware, which is the receive-latency bound `notes/05`
promised to earn rather than assert.

## Decision 4 — blocking is a proc-table state, waking is a mailbox event

`recv_wait` with nothing unseen moves the process to `blocked`. That is
a new ProcTable state, and it changes two existing rules:

* The seat unit evicts a BLOCKED resident when the run queue has
  waiters (the model's rule, currently unreachable because nothing
  blocks at M3).
* The mailbox writer, on enqueueing to a blocked process, marks it
  runnable and pushes it to the run queue. A message arriving is
  therefore a scheduling event generated by hardware — the first one in
  the machine that does not come from the rotation.

`recv_waitt` needs the timer wheel, which is the one genuinely new
subsystem; it can lag the untimed path by a pass.

## Decision 5 — immediates first, the serialiser second

A message is a term. Immediates (fixnum, atom, pid, nil) are one word
and need no heap at all — and ping-pong, the exit demo, is pure
immediates. Compound terms need the heap (deferred out of the barrel
engine at M3 pass 8) plus the serialiser that walks a term into a flit
stream and rebuilds it in the receiver.

So M4 runs the cheap half first: the demo works, the protocol is
proven, and the heap comes back with the serialiser that finally needs
it. This is the same ordering instinct that put the ROM before SdBoot
at M3 — get the loop closed, then widen it.

## Order of work

1. **This note**, then the shape-hash contract: `Encoding.shape_hash/1`,
   the RTL block, and a tripwire proving they agree.
2. **`Mailbox` RTL** — 32 × 64 ring, tombstones, enqueue/scan/take/skip,
   per-process counters and cursors. iverilog-first, standalone.
3. **`send`** — pid decode, the incarnation-serial check (a stale pid
   dead-letters, per `13`), hash, enqueue; `:mailbox_full` kills the
   RECEIVER (Q7).
4. **The receive family in the engine** — peek parks and scans, take and
   skip are one turn, wait blocks; ProcTable gains `blocked`, SeatUnit
   gains eviction and the mailbox gains the wake path.
5. **Heap re-integration + serialiser** — the wb2 path returns with
   per-seat result latches, and compound messages get copied.
6. **Ping-pong on silicon**, with the scan-distance histogram on the
   UART: the receive-latency bound, measured.

## Risks named up front

* The scan FSM and the swap/drain unit both want to park contexts; two
  parked contexts are fine, but a scan holding the mailbox port while a
  send wants to enqueue is a genuine two-writer question. Expect the
  enqueue to win and the scan to restart, or the mailbox to grow a
  second port properly.
* Blocked-resident eviction is the first path where a context leaves
  the pipeline for a reason the ROTATION did not choose. The pass-8
  finding (only a RUNNING context may be descheduled) says exactly where
  the sharp edge is.
* The model's `mailbox_depth` and the hardware's must agree, or the
  co-simulation lies. Fix both at 64 and assert it in the tripwire.

## Build log — passes 1–3 (2026-08-23)

| part | LUT4 | FF | DPR16X4 | DP16KD |
|---|---|---|---|---|
| ShapeHash | 16 | — | — | — |
| Mailbox (32 × 64 + matcher) | 350 | 200 | 16 | 5 |

Five EBRs, as the note predicted before the RTL existed. The whole
message subsystem — storage for 2,048 messages, per-process ring state,
and the match unit — costs less than 4% of what the register window
does.

### The shape hash, both halves, agreeing

`Encoding.shape_hash/1` (assembler) and `PicoBEAM.RTL.ShapeHash`
(mailbox writer) are generated from one definition and checked against
each other by `scripts/check_shape_hash.exs` + `scripts/tb_m4_shape.v`:
the Elixir side emits vectors, the Verilog side reproduces them. Nine
term shapes, agreement first run.

The packing deliberately keeps its lossy steps visible — arity
saturates at 7, atom indices keep three bits — because a collision
costs one wasted `peek` and nothing else. What it must never do is
disagree with itself, and that is exactly what the tripwire tests.

### What the mailbox testbench proves

FIFO order; a filtered peek reaching past two non-matching messages and
reporting scan distance 2; `take` removing from the MIDDLE and the
skipped messages surviving in order; a filter that matches nothing
leaving the cursor at the tail with nothing unseen, and a later arrival
becoming unseen again; per-process isolation including slot 31 at the
top of memory; and `full` at the ring limit.

That fourth one is the subtle one and it is the whole point of
selective receive: after `{500}` is plucked out of the middle, `{300}`
and `{400}` are still there, still in arrival order, still findable.

### One bug, of a familiar species

The scan's *decisions* were all correct on the first run — hit flags,
miss flags, scan distances, counts — but every returned WORD was
wrong. The matched word was being driven straight from the entry
store's output, and that store is a sync read: by the time the parked
context is resumed and reads the result, the memory's output has moved
on to a later probe. The flags were latched; the word was not.

Same family as M3's "latch the ret value per seat" and M2's
link-capture bug: **in a machine where the consumer of a value runs
turns later than the producer, every result needs a register, not a
wire.** Three times now. It is becoming this project's signature
failure, and naming it here is cheaper than finding it a fourth time.

## Pass 4 (2026-08-23) — `send`

63 LUT4. A send costs the sender ONE turn; everything expensive about
message passing at M4 is on the receiving side.

### The encoding change that made it free

`send rp, rm` reads two registers and writes none, so the pid and the
message now ride **f2/f3** — the slot's ordinary ra/rb read ports —
leaving f1 (the rd position) empty. `tset` already used this trick. The
alternative was a new "two sources, f1 and f2" address mux on every
slot; instead the engine needs nothing at all. Worth remembering as a
general move: when an op writes no register, its sources should occupy
the read ports the datapath already has.

### The incarnation check, in gates

    pid = tag_pid(5) | engine:4 | slot:6 | serial:22

Three tests gate delivery: it is a pid at all (else `:badarg` on the
SENDER — a program error, not a delivery failure); the engine field
names this engine (one engine at M4, so a remote pid dead-letters until
M6 gives it a ring to travel); and the target slot is occupied with a
**matching 22-bit serial**.

That last one is `notes/13`'s ABA guard made real, and the testbench
proves the case that matters: free a slot, drain the free list until it
is recycled, and the OLD pid — right slot, stale serial — dead-letters
while the CURRENT pid delivers. A restarted process can never receive
mail addressed to its predecessor.

The FIFO free list turns out to be load-bearing here, and the test had
to be rewritten to respect it: slots are reused as LATE as possible, so
the wall-clock gap between a pid dying and its slot answering again is
maximised. That was chosen at pass 2 for tidiness; it is a safety
property.

### Overflow kills the receiver, and the receiver may be anywhere

Q7's answer — backpressure on a sender would leak one process's
slowness into another's WCET — means a full mailbox kills the TARGET.
But the target may be resident on another seat, queued, or blocked, so
the kill cannot be a fault at X. ProcTable therefore gained a `doom`
command and a 32-bit `doom_vec`: the slot is marked with
`:mailbox_full` (reserved atom 7), the engine kills whichever seat
holds it, and the seat unit refuses to seat it. Alloc and free both
clear the bit, so a recycled slot never inherits a death — tested.

### The bug: a combinational loop between send and mailbox

`send` decided whether to enqueue from the mailbox's `full`, and
`full` was a function of the mailbox's `cmd` — which `send` drives. The
testbench hung with no output at all, which is the signature.

The fix is a dedicated **fullness probe port** (`q_slot`) addressed
independently of the command, with mirror-written head/tail replicas
behind it. The engine drives it straight from the decoded pid.

Third combinational loop of the project (after `drain_ready` in the
pass-3 testbench and `drain_ready` again in pass 5's harness), and all
three had the same shape: **a status output consumed by the very
signal that produces it.** A status port that a decision depends on
should never be addressed by that decision.

## Pass 5 (2026-08-23) — the receive family, and ping-pong

Processes talk.

    spawns=1  sends=40  recvs=40  rounds=20  deaths=1  faults=0

A root takes its own pid with `self`, hands it to a spawned `pong`
server as that process's argument, then bounces a counter back and
forth twenty times before reporting. Forty sends, forty takes, every
message an immediate — no heap, no serialiser, exactly as the note
planned in Decision 5.

### The receive family, split by what it costs

| op | cost | where |
|---|---|---|
| `recv_start` | 1 turn | X: mailbox `start`, clear the seat's filter |
| `recv_hash` | 1 turn | X: latch the filter (imm8) in the seat |
| `recv_skip` | 1 turn | X: mailbox `skip` |
| `recv_take` | 1 turn | X: mailbox `take`, rd ← the LATCHED peek word |
| `recv_peek` | park + scan | F-slot claim; the other three seats run |
| `recv_wait` | 0 or block | X: blocks only if nothing is unseen |

`recv_take` writing rd from the per-seat latched peek word — rather
than re-reading the mailbox — is the small win that keeps take at one
turn: by the protocol a take always follows a successful peek on the
same cursor, so the word is already in hand.

### The mailbox's command port is a seven-deep priority chain

    enqueue (send) ▸ X-stage start/skip/take ▸ an F-slot peek claim

One X context and one F context exist per cycle, so this is a priority,
not an arbiter — the seventh structure the barrel's one-owner-per-cycle
rule has made free. A scan that loses the port to an arriving message
simply resumes; a message that arrives mid-scan is found on the next
round, which is the race BEAM's receive loop already tolerates.

### The first scheduling event the rotation did not generate

`recv_wait` blocks a context (state 12) only when the mailbox reports
nothing unseen. A delivery to a blocked resident raises `unblock_en`
for its seat and the context resumes past its wait. Until now every
scheduling decision in this machine came from a counter; this one comes
from hardware noticing that a message arrived.

**Deferred, and named:** a blocked resident is not yet EVICTED in favour
of a queued runnable process. With four seats and few processes it
costs nothing (ping-pong holds two seats), but with more runnable
processes than seats it wastes slots. The eviction path needs a
`blocked` state in ProcTable plus a queue-side wake, and the mailbox
would then contend with the seat unit for `rq_push`. Next pass.

### Overflow reaches the resident

`send`'s overflow now dooms the target through ProcTable's doom
vector, deferred to a cycle when the seat unit is not commanding, and
the engine kills whichever seat holds a doomed slot — BarrelSeq gained
a `kill_en` for exactly this, because a doomed process may be sitting
on a seat with no bundle in X to fault.

### Cost

Whole engine with messaging: **12,300 LUT4 · 2,313 FF · 204 DPR16X4 ·
45 DP16KD**, up from M3's 10,292 / 1,861 / 166 / 40. Message passing —
storage for 2,048 messages, the match unit, the send path, the doom
vector and the wake logic — costs about **2,000 LUTs and 5 block
RAMs**, roughly a fifth of what the register window alone costs.

### The bugs

Both were mine in the testbench, and both were the same mistake in
different clothes: a probe that moved. When `count`/`unseen` migrated
to the mailbox's independent probe port, the send testbench kept
querying through the command slot; when the ping-pong testbench
stopped as soon as `out` fired, it sampled the death count one turn
before `halt` retired. Neither was RTL.

The RTL bug of this pass was caught by design rather than by test: the
scan's hit word is latched **per seat** (`rw0..3`) at the moment the
scan retires, because the parked context resumes turns later and the
mailbox's output has long since moved on. That is the fourth appearance
of this project's signature failure, and the first time it was written
correctly the first time — which is what a named pattern is for.

## Pass 6 (2026-08-23) — eviction, and the round trip that proves it

    spawns=5  evicts=4  sends=1  recvs=1  woke_with=99
    deaths=2  occ=4  faults=0

Five processes block on `receive` while only four seats exist. Blocked
residents are evicted so the root keeps running; the root then sends
ONE message to the FIRST waiter it spawned — the one most likely to
have been seated, blocked, and unseated — and that process is woken
from the evicted-blocked state, re-queued, re-seated, its window
restored, and resumed. It receives 99 and exits. The other four are
still blocked, still holding their slots.

That is the complete life cycle of a waiting Erlang process, in gates.

### `park` is not `save`

A descheduled process and a blocked one both leave their seat, and it
would have been easy to reuse one command for both. They are different:

    save (3)  → state = queued  → the run queue
    park (7)  → state = blocked → nowhere

**Only a message may make a waiting process runnable again.** If a
blocked process were queued, the scheduler would seat it, it would
re-run its `recv_wait`, find nothing, and block again — a busy-wait
dressed as a scheduler. The two commands exist so that cannot happen.

The wake is the mirror: `wake (8)` sets the state to queued and the
engine pushes the slot. Both halves are deferred until the ProcTable
command port and the run-queue push port are free, and the pending
wake retires only when BOTH have gone out — a wake that set the state
without queueing the slot would strand the process forever.

### Resuming at the same pc is the right answer

An evicted process saves the pc of its `recv_wait` itself, not the
bundle after it. So when it is re-seated it **re-runs the wait**, which
re-tests the mailbox. If the message that woke it has since been taken
by something else, or was not the one it wanted, it simply blocks
again. The condition is re-evaluated rather than assumed — the same
discipline that makes `receive` in BEAM a loop rather than a promise.

This fell out of the design rather than being engineered: `recv_wait`
blocks WITHOUT advancing pc, so the saved pc is already the right one.

### Where the rule now lives

`SeatUnit`'s deschedule test grew a fourth arm:

    exhausted AND waiters   → unseat to the queue tail, seat the head
    exhausted AND no queue  → reload the budget, keep the seat
    BLOCKED AND waiters     → unseat and PARK, seat the head
    seat empty AND waiters  → seat the head

All four evaluate at the owning seat's own F slot, so the whole
scheduler remains arbiter-free.

### Cost

Whole engine: **12,089 LUT4 · 2,328 FF · 204 DPR16X4 · 45 DP16KD** —
slightly SMALLER than pass 5 despite doing more, because the deferred
command paths let the synthesiser share logic that was duplicated
before. Eviction and the full wake round trip came for free.

Everything regresses: all six M3 unit testbenches, the spawn demo
(`values=[8 7 6 5 4 3 2 1]`), two concurrent recursions
(`results=[13 55]`), ping-pong (20 rounds), and the three M4 unit
testbenches.

## Pass 7 (2026-08-23) — M4 on silicon

Lines off the board, seconds apart, while ping-pong runs:

    p000 0 1 02 f6f f6e 0 0 de 01
    p000 0 1 02 5c9 5c8 0 0 8b 01
    p000 0 1 02 3a4 3a4 0 0 07 0c
    p000 0 1 02 9ff 9ff 0 0 b3 01
    p000 0 1 02 6c8 6c7 0 0 ed 0c
                │  │   │      │
                │  │   │      └─ block counter (×64 round trips)
                │  │   └──────── no evictions in this demo
                │  └──────────── takes
                └─────────────── sends
             occupancy = 2, deaths = 0

**Sends and takes never differ by more than one**, sampled at arbitrary
instants across hundreds of thousands of messages. One is a message in
flight; anything larger would be a message lost or duplicated. Two live
processes, nothing dying, the block counter racing through its byte.

Both 12-bit counters WRAP several times between consecutive UART lines
(~66 ms apart), which shows the rate is high but cannot measure it: a
wrapping counter sampled at random is not a measurement. `notes/18`
does it properly with a cycle-exact bracket and gets **52.5 cycles per
round trip** — about 229,000 round trips (458,000 messages) per second
at 12 MHz. An earlier draft of this note extrapolated "roughly a
million messages a second" from the wrap rate; that was an estimate
dressed as a result, and the benchmark replaces it.

### Two demos again

Default is ping-pong forever: the LEDs show a block counter whose speed
IS the message rate. Holding FIRE2 through a FIRE1 reset boots the
eviction demo instead — five waiters, four seats, one targeted wake,
`out` = 99 and `O` counting the evictions.

**M4 is complete.** Mailbox, shape hash, match unit, `send`, the full
selective-receive family, blocking, eviction and waking — in fabric, on
a board. What remains of the milestone as `07-roadmap.md` framed it is
the serialiser for COMPOUND messages, which waits on the heap's return
to the barrel engine; every message here is an immediate, which is what
Decision 5 planned for and what let the demo arrive this early.
